# Image Output Actions (Copy / Share / Save + Universal Regenerate) — Design

## Summary

Two independent, additive changes to assistant message actions:

1. **Regenerate chip works for every response, not just text-bearing ones.**
   Today `RegenerateChip` is nested inside a guard that only renders when
   the message has non-empty display text, so a pure image-generation
   reply (no text) shows no regenerate affordance at all. Decouple
   regenerate visibility from text presence so it appears for the last
   assistant message whenever it isn't streaming — text-only, image-only,
   or mixed.
2. **Long-press an image for Copy / Share / Save to Photos.** Any image
   rendered in the chat (user-sent or assistant-generated) gets a
   standard iOS context menu on long-press with those three actions.

## Background

OpenChat is a native Swift/SwiftUI iOS app. All chat content (text and
images) renders through one component, `MessageBubbleView.swift`, for
both `.user` and `.assistant` roles. Images — whether attached by the
user or generated by the model — flow through the same
`attachmentGallery(_:alignment:)` method (`MessageBubbleView.swift:238-260`).
There is no separate "image message" view and no message-type enum;
`ChatMessage` simply has an optional `content: String` and an optional
`imageAttachments: [ChatImageAttachment]`, and either or both can be
non-empty.

The existing icon-chip action row (`CopyChip`, `SelectChip`,
`RegenerateChip`, all private structs at the bottom of
`MessageBubbleView.swift`) is gated by:

```swift
if !displayContent.isEmpty {
    HStack(spacing: 4) {
        CopyChip(content: message.content)
        SelectChip(isPresented: $showingTextSelection)
        if isLastMessage && !message.isStreaming {
            RegenerateChip(action: onRetry)
        }
    }
}
```

`displayContent` strips calendar/memory action fences from
`message.content` but is empty whenever the message has no text — which
is exactly the case for a pure image-generation reply. That's the gap:
`RegenerateChip` is unreachable for image-only assistant turns even
though the underlying regenerate mechanism already supports them.

`ChatViewModel.regenerateLastReply()` (`ChatViewModel.swift:412-419`) is
already content-agnostic — it deletes the entire last assistant
`ChatMessage` (text and images together) and calls
`requestAssistantReply()`, which handles both `.text` and `.images`
stream events. No changes are needed there; this is purely a visibility
fix in `MessageBubbleView`.

For image actions, there's no existing precedent in this codebase —
tapping an image today only opens `ImagePreviewView` via
`previewAttachment` state (full-screen zoomable viewer, no action
buttons). The app already has `NSPhotoLibraryUsageDescription` in
`Info.plist` (read access, used elsewhere for image selection) but not
`NSPhotoLibraryAddUsageDescription` (write access, needed for Save to
Photos).

## Scope

- Regenerate chip: visible for the last assistant message whenever
  `!message.isStreaming`, regardless of whether it has text, images, or
  both.
- Long-press context menu on every rendered image (both `userBubble` and
  `assistantContent` paths, since both call `attachmentGallery`), with
  three actions: Copy, Share, Save to Photos.
- In a multi-image gallery, each image gets its own independent context
  menu acting only on that image.

### Out of scope

- No new "copy image" or "share" icon chip in the action row under the
  message — those actions live only in the image's long-press menu, per
  explicit direction.
- No batch "copy/share/save all images" action.
- No changes to `regenerateLastReply()` / `requestAssistantReply()`
  internals — the fix is UI visibility only.
- No changes to `CopyChip`/`SelectChip` behavior or visibility — they
  stay gated on `!displayContent.isEmpty` (text-specific actions).

## Architecture

### 1. Regenerate chip visibility

In `MessageBubbleView.swift`, split the single guard into two
independent conditions inside `assistantContent`:

```swift
#if canImport(UIKit)
if !displayContent.isEmpty {
    HStack(spacing: 4) {
        CopyChip(content: message.content)
        SelectChip(isPresented: $showingTextSelection)
        if isLastMessage && !message.isStreaming {
            RegenerateChip(action: onRetry)
        }
    }
} else if isLastMessage && !message.isStreaming {
    RegenerateChip(action: onRetry)
}
#endif
```

Result: text-bearing messages keep the full chip row unchanged;
image-only messages (and any other content shape that leaves
`displayContent` empty) get just the regenerate chip, when eligible.

### 2. Image long-press actions

New private view wrapping each attachment's image in `attachmentGallery`,
replacing the bare `Image` inside the existing `Button`. The tap gesture
(open `previewAttachment`) and the long-press context menu coexist on the
same view — standard SwiftUI behavior, no gesture conflict.

```swift
.contextMenu {
    Button {
        UIPasteboard.general.image = uiImage
        Haptics.light()
    } label: {
        Label("Copy", systemImage: "doc.on.doc")
    }

    Button {
        shareAttachment = attachment
    } label: {
        Label("Share", systemImage: "square.and.arrow.up")
    }

    Button {
        saveToPhotos(uiImage)
    } label: {
        Label("Save to Photos", systemImage: "square.and.arrow.down")
    }
}
```

New state on `MessageBubbleView`, following the existing
`previewAttachment` pattern:

```swift
@State private var shareAttachment: ChatImageAttachment?
```

New `.sheet(item: $shareAttachment)` modifier (alongside the existing
`.fullScreenCover(item: $previewAttachment)`) presenting a small new
`ActivityShareSheet: UIViewControllerRepresentable` that wraps
`UIActivityViewController(activityItems: [uiImage], ...)`.

New private method for Save to Photos:

```swift
private func saveToPhotos(_ image: UIImage) {
    PHPhotoLibrary.requestAuthorization(for: .addOnly) { status in
        guard status == .authorized || status == .limited else {
            Task { @MainActor in Haptics.error() }
            return
        }
        PHPhotoLibrary.shared().performChanges {
            PHAssetChangeRequest.creationRequestForAsset(from: image)
        } completionHandler: { success, _ in
            Task { @MainActor in success ? Haptics.success() : Haptics.error() }
        }
    }
}
```

(`import Photos` added to `MessageBubbleView.swift`.)

**Info.plist:** add `NSPhotoLibraryAddUsageDescription` — the narrower
"add-only" permission string, distinct from the existing read-access
`NSPhotoLibraryUsageDescription`:

```xml
<key>NSPhotoLibraryAddUsageDescription</key>
<string>OpenChat saves images to your photo library when you choose Save to Photos.</string>
```

## Error Handling

- Save to Photos: authorization denied or restricted →
  `Haptics.error()`, no alert (consistent with the app's existing
  lightweight haptic-only feedback pattern; no toast/alert system exists
  today for this kind of action).
- Save to Photos: `performChanges` completion `success == false` (e.g.
  disk full) → `Haptics.error()`.
- Copy/Share: no failure mode to handle — `UIPasteboard` assignment and
  presenting the system share sheet cannot fail in a user-visible way.
- Regenerate chip: no new error handling — reuses the existing
  `onRetry` closure and `regenerateLastReply()` guard (`!isStreaming`).

## Testing

- Manual verification in the simulator (this app has no existing unit
  test coverage for `MessageBubbleView` or `ChatViewModel`'s streaming
  paths, per the precedent noted in the edit-previous-messages spec):
  - Generate an image-only assistant reply (no text) → confirm the
    regenerate chip appears and regenerating replaces the image.
  - Confirm regenerate still works unchanged for text-only and mixed
    text+image replies.
  - Long-press a user-sent image and an assistant-generated image →
    confirm Copy/Share/Save to Photos all appear and each works
    (paste into Notes, share sheet opens, image lands in Photos).
  - Deny photo library add permission → confirm Save to Photos fails
    gracefully (error haptic, no crash).
  - Multi-image assistant reply → confirm each image's context menu
    acts only on that image.
